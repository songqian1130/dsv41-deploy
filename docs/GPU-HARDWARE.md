# 五卡硬件基线（2026-11-16 实测）

> 起因：换卡位后引擎从 54 tok/s 降到 50，怀疑「GPU4 性能差」。
> 结论：**五张卡性能完全一致，GPU4 的算力和带宽都是最高一档。**
> 但 GPU4 有另一个完全独立的问题——**PCIe 大块搬运 + kernel 重叠会硬冻结整机**，
> 那是稳定性问题，不是性能问题。两件事不要混。

## 1. 规格（`nvidia-smi --query-gpu=...` 逐项）

| 项 | 五卡的值 | 是否一致 |
|---|---|---|
| 型号 | NVIDIA CMP 170HX (GA100) | ✅ 完全一致 |
| 显存 | 65536 MiB | ✅ |
| SM 时钟上限 | 1695 MHz | ✅ |
| 显存时钟上限 | 1728 MHz | ✅ |
| PCIe 最大链路 | Gen2 ×16 | ✅ |
| PCIe 当前链路 | **Gen2 ×4** | ✅ 五卡都被主板限制在 x4 |
| NUMA 归属 | 全部 `numa_node = -1` | ✅ 内核看不到双路划分 |
| 卡间拓扑（`topo -m`） | 全部 `PHB` | ✅ 无 NVLink、无 switch |

**五张卡都在 `[0000:00]` domain 下**，`00:02.0~02.3` 和 `00:03.3` 都是 CPU0 的
PCIe Root Port（`lspci -tv` 确认），**不是跨 CPU**。

## 2. 实测数据

容器内 `dev0~3` 对应宿主 **GPU1 / GPU2 / GPU3 / GPU4**（用 UUID 对齐确认）。

### 2.1 算力（fp16 8192³ matmul，交错顺序跑两遍）

| 宿主 GPU | 第一次 | 第二次 | 均值 | 波动 |
|---|---:|---:|---:|---:|
| GPU1 | 157.82 | 157.49 | 157.65 | 0.2% |
| GPU2 | 158.60 | 159.41 | 159.01 | 0.5% |
| GPU3 | 158.76 | 158.58 | 158.67 | 0.1% |
| **GPU4** | **159.41** | **161.24** | **160.33** | 1.1% |

**GPU4 最高（+1.7%）。**

> ⚠️ 别用 4096³ 小矩阵测。第一次用 4096³、按 0→1→2→3 顺序跑，得到
> GPU1 170.6 / GPU2 146.3 / GPU3 145.8 / GPU4 143.5，看起来"越跑越慢"。
> 那是顺序执行时前面几张卡温度/boost 状态不同造成的假象，换成 8192³ +
> 交错顺序（0,1,2,3,3,2,1,0）后五卡落在 157.5~161.2。

### 2.2 主机→显存（pinned buffer，`copy_(non_blocking=True)` + synchronize）

| 宿主 GPU | 64 MB 带宽 | 1 MB 带宽 | 4 KB 延迟 |
|---|---:|---:|---:|
| GPU2（dev1） | 1.47 GB/s | 1.47 GB/s | 18.3 μs |
| GPU3（dev2） | 1.51 GB/s | 1.48 GB/s | 19.0 μs |
| **GPU4（dev3）** | **1.51 GB/s** | 1.48 GB/s | 19.0 μs |

带宽贴着 **PCIe Gen2 ×4 ≈ 1.6 GB/s** 的上限，五卡一样。
GPU4 的小包延迟高 3.8%（19.0 vs 18.3 μs），是全组唯一能测出来的差异，量级 0.7 μs。

### 2.3 卡间 P2P

`torch.cuda.can_device_access_peer` 对全部 6 对组合返回 **True**。

⚠️ **带宽/延迟没有测成**：跑 32 MB × 40 次跨卡拷贝时，整机硬冻结
（见第 4 节）。这个测试**不要在 GPU4 在场时重做**，要做也必须先把 GPU4
从容器里拿掉，且不能与任何 matmul 同时进行。

## 3. 所以「GPU4 性能差」这个印象从哪来

| 可能的来源 | 实际情况 |
|---|---|
| 11-06 记录「GPU4 只跑到 0~65% 利用率」 | 那是死机前的最后 200 ms，流水线还没流到第 21 层，不是它慢 |
| 11-06 记录「GPU0-3 限 150W、GPU4 **200W**」 | GPU4 的功耗上限反而**最高**，单卡实测跑到过 316 W |
| 11-14 记录「GPU4 200→150W」 | 是主动降的，为了压整机峰值 |
| 换卡后 54 → 50 | 见 `bench/README.md` 3.1 节：热身不足是最可能的解释，**待 A1 vs A2 对照坐实** |

## 4. 与冻结的关系（重要：两个独立问题）

| 维度 | 结论 |
|---|---|
| **性能** | 五卡一致，GPU4 略优。用它做 rank3 不会因为"算得慢"拖后腿 |
| **稳定性** | GPU4（`09:00.0`，根端口 `00:03.3`）在 **PCIe 大块搬运与 GPU kernel 时间重叠**时硬冻结整机 |

2026-11-16 17:00 又验证了一次：容器在 GPU1-4 上跑引擎，先做了 8192³ matmul
（kernel），紧接着做 32 MB × 40 次 GPU3→GPU4 P2P 拷贝 —— 连接立即断开，
之后 ping 100% 丢包、SSH 超时，**硬冻结，需断电**。
这次没有任何 ComfyUI 参与，只有引擎容器自身的 CUDA 活动，坐实了"GPU4 自己就有问题"。

详细定位过程见 [`GPU4-HANG.md`](GPU4-HANG.md)。

## 5. 待查（重启后）

```bash
# GPU4 链路有没有累积可纠正错误（有 → 链路质量问题，能解释延迟 +3.8% 和冻结）
sudo lspci -vvv -s 09:00.0 | grep -A3 -i "Advanced Error Reporting"
sudo lspci -vvv -s 09:00.0 | grep -iE "Correctable|Uncorrectable|CESta|UESta"
sudo dmesg | grep -iE "AER|pcieport.*error|09:00" | tail -20

# 对比同一 IIO 下的 GPU3
sudo lspci -vvv -s 05:00.0 | grep -iE "Correctable|Uncorrectable"
```

判读：
- GPU4 有 non-zero `Correctable` 计数而 GPU3 没有 → 链路有问题，值得换插槽/换线（这台是转接线 + x4 转接板）
- 两者都干净 → 冻结属于更深层（供电/固件/魔改卡），换插槽做物理对调是唯一剩下的验证

### 对调实验状态（2026-11-17 08:39 开机，实验开始）

- **嫌疑卡 1322321055006**（原 GPU4）跑 ComfyUI（250W，H2D 大块搬运的发起者）
- 配置落点与档案预言一致：`CUDA_VISIBLE_DEVICES=0` 使 ComfyUI 留在 02:00.0，

- 250W drop-in 已改绑 UUID `29ed6f48`（跟 ComfyUI 角色走，不再跟旧卡走）——
  修正了 11-16 档案"无需改配置"的疏漏：CUDA_VISIBLE_DEVICES 确实不用改，但

### 对调实验结果（2026-11-17 上午，三关全过）

| # | 考验 | 内容 | 结果 |
|---|---|---|---|
| 1 | 单卡致命配置 | GPU4（09:00.0 槽 + fa5de0a2）：stage 0.87GB/s + 32GB 常驻 + SM + DRAM 10GB/s，150s | **存活** |
| 2 | 单卡致命配置 | GPU0（02:00.0 + 嫌疑卡 29ed6f48）：同款，150s | **存活** |
| 3 | **死亡场景 ×5 轮** | `death_test.sh`（引擎 6 路满载 180s + ComfyUI H3 124 帧，09:13-09:31 连续 18 分钟） | **5/5 存活** |

**解读**：
- 对调后的新组合（嫌疑卡跑 ComfyUI/H2D 风暴 + fa5de0a2 在 09:00.0 扛最重 21 层）
  完整复刻了 11-17 凌晨的死亡形态，无一死亡 → **对调瓦解了原触发组合**（80% 置信度）。
- 诚实边界：凌晨是 6.3h 才中招的概率性竞态，5 轮 ≈18min 暴露时长只有 1/20——
  结论是"**短时间内不触发**"，最终审判靠生产长期观察：**死机跟随卡（嫌疑卡在哪哪死）
  → 卡问题；跟随槽（09:00.0 谁在谁死）→ 槽问题**。
- 单卡层面两卡两槽都过审，"卡单卡就死/槽单卡就死"的强形式已排除。

**工具链沉淀**：`bench/`（synthetic_load.py / synthetic_test.sh / sweep_cards.sh /
death_test.sh / engine_busy.py）+ 服务器 `~/manju/`（death_sweep5.sh 自动跑 5 轮）。
death_test 的 `ENGINE_BASE` 默认 18000，**生产必须传 9010**。

### 对调后性能验证（2026-11-17 09:50-09:57，label `swap-1m-099c`）

| 口径 | wall | decode | 判定 |
|---|---|---|---|
| 基线（11-16 `t1m-099`，对调前） | 50.43 | 57.55 | — |
| **对调后 6 轮均值** | **51.03** | **58.83** | **无回退**（+1.2%/+2.2%，轮间噪声内；run 波动 49.0-53.9） |

⚠️ **两个前置坑（基准前必查）**：
1. **fastwatch（5Hz nvidia-smi 采样）开着会让性能腰斩**（实测 26.46 vs 51.03）——
   nvidia-smi 查询与 CUDA 驱动锁竞争。fastwatch 只在死机取证实验时开，**日常/基准必须停**。
2. 看门狗 timer（3 分钟周期 health.service）会偶发打爆单个 case（实测 zh 87s 崖 + TTFT 21s，
   正好撞触发时刻）；基线口径 timer 是开的，对标基线时开着亦可，但要能识别这种坑。
3. 一次 6 路 death_test 后专家缓存冷，**基准热身至少 4-5 轮**（39.6→44.5→46.5→48.9→49.3→52+）。

统计噪声：`tps_decode` 偶发崩到 1-2（wall 正常）——引擎自报 decode 时间异常值，分析看 wall 或剔除。

### 判读协议（长期有效，按此归因）

1. 开机后第一件事：`nvidia-smi --query-gpu=index,pci.bus_id,serial --format=csv,noheader` 重对表
   ——卡会换 index，**认 S/N 不认 index**。
2. 死机归因（实验观察期）：
   - 死机发生在 **ComfyUI 大任务期间**（嫌疑卡在 02:00.0）→ **卡问题**（1322321055006 跟着死）
   - 死机发生在 **纯引擎负载**（09:00.0 槽位上的 1322321009839）→ **槽问题**（09:00.0/00:03.3 跟着死）
   - 长期两边都不死 → 原组合（嫌疑卡×原槽位）竞态，或已随功耗/负载结构改变消失
3. 判死机时先 `nvidia-smi --query-gpu=index,serial` 确认死机时刻谁在忙，再按上条归因。
