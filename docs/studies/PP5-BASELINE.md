# PP5 固定基线（cases_v1）

> 目的：以后不再重复"先测一遍基线"。任何新模式/新参数都只跑 `run_cases.py`、只和这里比。
> 用例库 `bench/cases_v1.json`，sha256 `ee98f898…`，脚本启动即校验。

## ⚠️ 已定论，不要再用单次采样推翻

**新 PP5（dspark）在代码类负载上比旧引擎快 19%**：`code_python` 五轮均值 **51.80** vs 43.46。
完整样本与推导见 `bench/PP5-SPEED-EVIDENCE.md`（自动生成，含 23 个样本的接受率与步时）。

判 dspark 快慢必须满足三条，否则数据作废：
1. **用 `real` 集合**（代码/JSON/技术解释），不要只用高熵随机文本；
2. **跳过冷启动第一个样本**，取后续稳态；
3. **至少 3 轮采样取均值**，接受率在 2.14~3.53 之间跳，单次没有意义。

## 1. 为什么用服务端计数器，而不是客户端流式时间戳

2026-11-14 在 ram 模式上做的对照实验（`/tmp/probe_metrics.py`、`/tmp/probe_step.py`）：

| 来源 | TTFT | 单 token 间隔 |
|---|---:|---:|
| 引擎自报（`/metrics`） | **0.378 s** | **23.1 ms** |
| 客户端流式 chunk | 3.83 s | 23 ms（但 29 个 chunk 装了 116 token） |

结论：detokenizer 会把多个 token 合并成一块并延后发送，**客户端 chunk 时间戳既不能测 TTFT 也不能测 ITL**。
`23.1 ms` 才与 `300 token / 6.907 s decode = 43.4 tok/s` 自洽。

因此 bench_v1 统一用 `/metrics` 的引擎自报值：

| 指标 | 公式（取本用例前后两次快照的增量） |
|---|---|
| TTFT | `Δ vllm:time_to_first_token_seconds_sum / Δ ..._count` |
| 单流 decode | `Δ vllm:generation_tokens_total / Δ vllm:request_decode_time_seconds_sum` |
| ITL | `Δ vllm:inter_token_latency_seconds_sum / Δ ..._count` |
| 聚合吞吐（并发） | `Δ generation_tokens_total / 客户端墙钟` |

请求体固定：`temperature=0`、`stream=false`、`max_tokens` 见下表。

## 2. 固定用例（两套，均固化在 `bench/cases_v1.json`）

### 2.1 用例库是唯一来源，脚本不再生成随机 prompt

`cases_v1.json` 里存的是**正文常量**，`sha256 = ee98f8987efaa5f5b5402eb4c54b0c22745ebe51856474df7ddec2bd68e457f9`。
`run_cases.py` 启动时会重算 hash，与文件声明不符就**直接退出**——防止改了用例还复用旧结果。
要改用例必须新建 `cases_v2.json` 并升版本号。

### 2.2 唯一允许变化的是 nonce

旧做法是每次换 seed 生成全新随机文本，绕缓存有效但样本严格说不可比。
现在改成：

```
prompt = "[run0031-C1_decode-0]\n" + 固定正文
```

- 正文一字不改 → 样本完全可比；
- nonce 每轮唯一 → 前缀从头就不同，缓存必然失效 → 冷启动仍然真实；
- 代价只有约 8~12 个 token，长度差异记录在结果里。

### 2.3 两套用例

| 集合 | 用例 | 提示 | 输出上限 | 并发 | 测什么 |
|---|---|---|---:|---:|---|
| `bench` | `C1_decode` | 正文 249 字 ≈ 420 tok | 400 | 1 | 单流 decode、ITL |
| `bench` | `C2_ttft22k` | 正文 13,015 字 ≈ 22,000 tok | 64 | 1 | 冷启动 TTFT |
| `bench` | `C3_conc3` | 3 份互不相同的 2,741 字 ≈ 4,640 tok | 300 | 3 | 并发聚合、TTFT 抖动 |
| `real` | `code_python` | 写线程安全 LRU + pytest | 500 | 1 | 代码生成：dspark 最友好 |
| `real` | `json_struct` | 转 JSON，强格式约束 | 400 | 1 | 结构化输出 |
| `real` | `zh_tech` | 解释 PagedAttention 到内存布局 | 500 | 1 | 中文技术解释 |
| `real` | `math_steps` | Σn² 推导 | 400 | 1 | 高度可预测的推导过程 |

**为什么要两套**：`bench` 的正文是随机汉字散列，可预测性极低，会把 dspark 的投机接受率压到 2.48，
**严重低估 dspark**（62 ms 步时 × 2.48 = 36 tok/s；同一台机器上接受率 5.0 时就是 80 tok/s）。
`real` 才代表真实业务分布。两者必须分开看，不能混为一谈。

第二个参数是 `run_index`，只影响 nonce（`run0061`），不再影响 prompt 内容。

### 模式 `legacy`（同引擎，engram 走 SSD）— 不单独建基线、不补测
旧数据是客户端 chunk 口径（TTFT 11.92 s / 41.8 tok/s），**不再为它专门切模式跑 bench_v1**。

理由：legacy 与 `ram` 只差 engram 的存放位置，decode 阶段完全不读 engram，所以单流 decode 直接沿用 `ram` 的 **43.18 tok/s** 作为参考值；TTFT 只保留旧口径 11.92 s 记账，不与上表横比。

什么时候会有真数据：哪天因为别的原因切到 legacy，顺手跑一次 bench_v1 补上即可。**绝不为了补基线去切模式。**

### 模式 `dspark`（新引擎 V2 + dspark k=3 + 20 层专家在 CPU + engram 走 SSD）
2026-11-14 11:26 / 11:27，`run_index=41, 51`，两次一致：

| 用例 | 输入 tok | 输出 tok | TTFT | decode tok/s | 墙钟 tok/s | 每步 ITL | 墙钟 |
|---|---:|---:|---:|---:|---:|---:|---:|
| C1_decode | 415 | 400 | 1.62 s | **35.36** | 30.91 | 69.4 ms | 12.94 s |
| C2_ttft22k | 22,073 | 64 | **10.51 s** | 31.09 | 5.09 | 66.4 ms | 12.58 s |
| C3_conc3 | 3×4,637 | 3×300 | 8.49 s | 15.67（每流） | **32.01（聚合）** | 126 ms | 27.6 s |
| C1_decode（复测） | 400 | 400 | 1.11 s | 36.47 | 33.10 | 62.0 ms | 12.09 s |

引擎自报的投机数据：`Mean acceptance length 2.48~3.20`、逐位接受率 `0.772 / 0.516 / 0.193`、`Avg Draft acceptance rate 56.3%`。

**解读**：dspark 的每步 ITL 是 62~69 ms（ram 模式只有 23 ms），原因是 20 层专家的 MXFP4 权重常驻主机内存、每步都要读；
它换来 2.48 token/步，净效果 **36 tok/s < 43.2 tok/s**。要追平 ram 模式，接受长度得 ≥3.0（即接近 100% 接受率），不可能达到。

#### 2026-11-14 12:26 用固定用例库复测（cases_v1，nonce=run0041）

同一份 `cases_v1.json`，ram 与 dspark 各跑一遍，这是最干净的 apples-to-apples：

| 用例 | ram decode | dspark decode | dspark 步时 | acc/draft | 每步 token |
|---|---:|---:|---:|---:|---:|
| `code_python` | 43.46 | 37.98 | 77.0 ms | 0.639 | 2.92 |
| `json_struct` | 43.56 | 35.05 | 86.5 ms | 0.677 | 3.03 |
| `zh_tech` | 43.42 | 32.30 | 69.7 ms | 0.531 | 2.59 |
| `math_steps` | 43.45 | **20.02** | 139.7 ms | 0.612 | 2.84 |
| `C1_decode` | 43.18 | 31.46 | 68.0 ms | 0.506 | 2.52 |
| `C2_ttft22k` | 42.70 | **45.05** | 67.6 ms | 0.667 | ~3.0 |
| `C3_conc3` | 21.65/流 | 20.47/流 | 113 ms | 0.582 | — |

**没有复现"新 PP5 单流 50/60/80"**。最好的一档是 `C2_ttft22k` 的 45.05（输出只有 64 token，接受率被抬高），
稳态长输出落在 20~38。

**物理上限（硬约束，值得记住）**：
`k=3` 意味着每步**最多 4 个 token**（3 draft + 1 bonus）。所以

```
最大 decode = 4 / 步时
```

- 当前步时 68 ms → 理论上限 **58.8 tok/s**（且要 100% 接受，实际做不到）
- 要到 80 tok/s，必须步时 ≤ 50 ms，**或**把 k 提到 5（每步最多 6 token）

而实测步时是 68~140 ms，`math_steps` 甚至 139.7 ms（某些内容触发大量 CPU 专家读取）。
所以 50/60/80 只可能来自两种情况：
1. **步时被压到 40~50 ms** —— 也就是专家不下放、全在卡上的配置；
2. **k=5 或更大的投机深度** —— 当前配置是 k=3。

这两条都还没验证过，正好是下一步要做的。

#### ⚠️ 2026-11-14 13:08 修正：上面"dspark 净亏"的结论**是错的**

同一套用例连续跑 5 轮（共 20 个样本），预热后的真实分布：

| 用例 | 冷启动首轮 | 预热后 4 轮 | 均值 | ram | 差 |
|---|---:|---|---:|---:|---:|
| `code_python` | 37.98 | 53.74 / 52.57 / 51.11 / 49.79 | **51.80** | 43.46 | **+19%** |
| `json_struct` | 35.05 | 35.33 / 35.81 / 43.81 / 39.78 | 38.68 | 43.56 | −11% |
| `zh_tech` | 32.30 | 36.09 / 35.29 / 41.04 / 41.52 | 38.49 | 43.42 | −11% |
| `math_steps` | 20.02 | 26.31 / 38.25 / 38.84 / 41.76 | 36.29 | 43.45 | −17% |

**代码类负载上 dspark 确实比旧引擎快 19%，用户"新 PP5 基本都在 50"的观察成立。**

之前得出"净亏"是三个偏差叠加的结果，全部记下来避免再犯：
1. **用例偏差**：用高熵随机汉字（为了绕前缀缓存），而这恰好是投机接受率最低的文本。
2. **冷启动偏差**：每轮第一个样本明显偏低（37.98 vs 后续 53.7），CUDA graph / 专家 LRU / page cache 都是冷的。
3. **单次采样**：接受长度在 2.14~3.53 之间跳（日志实证），单跑一次根本没代表性。

**正确的速度模型**：
```
decode = (1 + 3 × acc_per_draft) / 步时
```
- 接受率 0.85 → 3.55 token/步 ÷ 66 ms = **53.8 tok/s**
- 接受率 0.50 → 2.50 token/步 ÷ 66 ms = 37.9 tok/s
- 日志里 `Mean acceptance length` 实测区间 2.14~3.53，这就是 32~54 tok/s 的全部来源。

**结论改为**：dspark 不是净亏，而是**分负载**——代码/结构化任务赢旧引擎 19%，开放文本输 11~17%。
要不要让它当生产，取决于日常负载是代码还是散文。

### 与 `ram` 的对比（同一套用例，服务端口径）

| 指标 | `ram` | `dspark` | 结论 |
|---|---:|---:|---|
| C1 单流 decode | **43.18** | 36.47 | ram 快 18% |
| C1 每步 ITL | **23.2 ms** | 62.0 ms | dspark 每步慢 2.7 倍 |
| C2 22k 冷启动 TTFT | **6.45 s** | 8.63~10.51 s | ram 快 30%+ |

结论：**5 卡上 dspark 不划算**。它的收益（2.5 token/步）小于代价（每步 2.7 倍）。
