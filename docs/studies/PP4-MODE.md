# PP4 模式（4 卡，第 5 卡留给 ComfyUI）

由 PP5 `fast` 派生。目标：**腾出 GPU4 跑 ComfyUI，同时保住 40 tok/s 以上的单流速度。**
实测达标（46~74 tok/s），代价是 TTFT 从 9.4 s 涨到 13.7 s。

## 1. 唯一硬约束：最后一段必须 ≥21 层

```python
# hybrid.py:101
or sum(layers[:-1]) > 19
raise ValueError("pipeline_layers must partition 40 layers across PP stages,
                  with layers 19–39 on the last stage")
```

**前 3 段合计只能是 19 层**，最后一段吃 21 层。所以 PP4 不是 `10,10,10,10`，
只能形如 `[6,6,7,21]` / `[5,5,5,25]` / `[7,6,6,21]`。

根因：layer 20 是 `candidate_source` 枢纽层（`kv_source_layer_ids=[2,8,14,20]`，
24/28/32/36 层消费它写的 buffer），必须和 19 层同段。

> 公开参考 `zebgop-ops/dsv41flash-pp` 用 `8,12,8,12`，是因为它打了 `pp_shadow.py`
> 补丁让后段重建源层注意力。我们没这个补丁，**不要照抄那个分区**。

## 2. 选 `[6,6,7,21]` 而不是 `[5,5,5,25]` 的原因

前 19 层（0~18）的专家**必须整层常驻各自 GPU**——CPU 下放窗口固定是 20~39
（`CPUMoEConfig.start_layer=20, end_layer=40` 默认值，hybrid.py 不覆盖）。

| 分区 | 前 3 段每卡专家 | 说明 |
|---|---|---|
| `[5,5,5,25]` | 33.8 GiB × 3 | 前段宽松，末段 25 层 |
| `[6,6,7,21]` | 40.5~47.3 GiB × 3 | **均摊最紧，但末段最小** |
| `[8,8,3,21]` | 54.1 GiB × 2 | 单卡装不下（+KV+激活 > 64 GB） |

单层权重（从 safetensors 头部实算）：

```
每层 dense（注意力/归一化） = 0.125 GiB
每层专家 384 个             = 6.757 GiB
embed / head                = 1.233 GiB 各一份
合计 40 层专家              = 270.3 GiB   ← 模型几乎全是专家
engram 两张表（layer 1 名下）= 189.2 GiB   ← 走 SSD，不占显存
```

## 3. 少一张卡的真实代价：专家驻留率腰斩

| | PP5 `fast` | PP4 |
|---|---:|---:|
| 专家缓存槽位 | 7216 / 7680 | **4320 / 7680** |
| 驻留率 | 93.96% | **56.25%** |
| 缓存总量 | 126.1 GiB | 75.6 GiB |
| **GPU 命中率（实测）** | **99.5~99.73%** | **93.18~94.61%** |
| **CPU 路由占比** | **0.27%** | **6.8%（25 倍）** |

命中率只掉 5~6 个百分点，但 CPU 要算的量涨了 25 倍 —— 这是 PP4 变慢的**唯一主因**。
（不是因为 pipeline 少一段，也不是因为分区不均衡：batch=1 时五段本来就串行。）

## 4. decode 线程必须从 4 提到 16

PP5 的 decode 4 线程是「CPU 几乎没活，越少越省」；PP4 反转了：

| decode 线程 | code | json | zh | math | ITL（code） | PP3 CPU |
|---|---:|---:|---:|---:|---:|---:|
| 4 | 59.4 | 51.8 | **29.0** | 41.5 | 75.2 ms | 401%（打满） |
| **16** | **70.2** | **62.4** | **46.6** | **55.7** | **57.9 ms** | 饱和 |
| 20 | 73.9 | 64.3 | 47.5 | 56.1 | 61.0 ms | 饱和 |

- **4 线程时 zh_tech 只有 29.0，不达标**；16 线程把它拉到 46.6（+61%）。
- 为什么 PP4 能开 16 而 PP5 不能开 28：PP5 是 5 个 rank，PP0~PP3 各要吃 1 核；
  PP4 只有 4 个 rank，`16 + 3×1 + 1 ≈ 20 < 28` 物理核，仍不超订。

### 4.1 16 vs 20 线程：配对复测结论是「没有差异」

单轮采样会骗人 —— **同一配置不同 nonce 之间就能差 5~7%**。所以用同一批 nonce（101/102/103）配对跑三轮：

| 用例 | t16（101/102/103） | 均值 | t20（101/102/103） | 均值 | 配对差 |
|---|---|---:|---|---:|---:|
| code_python | 71.38 / 76.55 / 75.88 | 74.60 | 70.64 / 77.59 / 73.19 | 73.81 | **−1.1%** |
| json_struct | 62.17 / 64.67 / 66.33 | 64.39 | 65.97 / 62.05 / 66.76 | 64.93 | **+0.8%** |
| zh_tech | 45.86 / 49.68 / 47.69 | 47.74 | 46.34 / 48.63 / 48.26 | 47.74 | **0.0%** |
| math_steps | 53.71 / 56.40 / 60.18 | 56.76 | 52.70 / 57.36 / 58.98 | 56.35 | **−0.7%** |

逐 nonce 配对差值在 −3.5%~+6.1% 之间来回跳，**没有一致方向**。

早先那轮「t20 高 2~5%」是因为 t16 那一次刚好抽在低端（单轮 70.2~73.7，而三轮均值 74.6）。
**结论：16 线程已经到 CPU 并行度饱和，再加 4 个线程不产出 token。定稿用 16。**

## 5. 实测（2026-11-14，cases_v1，全冷启动）

| 用例 | PP5 `fast`（k=5） | **PP4（16 线程，三轮均值）** | 保留率 |
|---|---:|---:|---:|
| code_python | ~96~100 | **74.6**（71.4~76.6） | 76% |
| json_struct | ~84~85 | **64.4**（62.2~66.3） | 76% |
| zh_tech | ~61~65 | **47.7**（45.9~49.7） | 76% |
| math_steps | ~79 | **56.8**（53.7~60.2） | 72% |
| C1_decode（高熵最差，单轮） | — | 51.6 | — |
| **C2_ttft22k** | **9.40 s** | **13.71 s** | 退步 46% |
| C3 三路并发（单轮） | — | 23.5 / 每流（ITL 99.6 ms） | — |
| 显存占用 | 5 卡 | **GPU0-3 用满，GPU4 = 0 MiB** | — |

**结论：单流 48~75 tok/s（四档均值 61），达到「40 多到 50」的验收线，且 GPU4 完全空出来。**

TTFT 退步的原因同 decode：22k prefill 会把 token 路由到每层全部 384 个专家，
CPU 上的专家从 464 个涨到 3360 个，而 prefill 的瓶颈正是 PP4 段（PP3）的 CPU 计算。

## 6. 怎么用

```bash
sudo dsv41-pp5-ctl.sh use pp4     # 切到 4 卡（GPU4 空出来给 ComfyUI）
sudo dsv41-pp5-ctl.sh use fast    # 切回 5 卡（默认生产）
sudo dsv41-pp5-ctl.sh status      # 看模式/容器/健康/显存
```

- 模式表在 `/usr/local/bin/dsv41-pp5-ctl.sh` 的 `MODES`，模式文件 `/etc/dsv41-pp5/mode`
- 两种模式都用 **9010 端口**，看门狗不需要改
- 切换会自动停掉另一种模式的容器（`drop_others`）
- 切换后要等约 12 分钟加载；看门狗 3 分钟一轮，`WARMUP_SEC=2100` 内不会误杀

**ComfyUI 注意事项**：PP4 只占 GPU0-3，GPU4 全程 0 MiB。但换回 `fast` 会占满 5 卡，
所以 ComfyUI 必须在 PP4 模式下用。主机内存方面 PP4 约占 150 GiB（20 层 CPU bank 138 GiB），
247 GiB 总量下 ComfyUI 还有 ~70 GiB 可用。
