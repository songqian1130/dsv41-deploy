# 方案卡标准（v1.1）

每个方案（一次参数调整、一次引擎改动、一次分区变更）结束时的**唯一输出格式**。
目的有三个：你能 3 秒读懂、多方案能横向对齐、三个月后能复现。

> 硬规则：**六段的顺序、行名、单位、小数位都不许改**。可以留空写「未测」，但不许换名字、
> 不许换单位、不许新增同义行。可比较性全部来自这一点。
>
> **三条附加硬规则（2026-11-14 23:10 起）**
> 1. **引擎必填**，且必须写成「家族 + 镜像 tag + 镜像 ID + 源码 commit + 补丁文件名 + **补丁作者**」六项。
>    第六项是 2026-11-14 加的：不知道补丁是谁写的时候就写不出「我们改了什么」，也谈不上合规。
>    同一个模型换一代引擎能差 90%，不写引擎的数字三个月后无法解释。
>    光有 tag 不够：本仓库的三个镜像里有两个**不在任何 registry**，还有一个**自带未提交改动**，
>    只写 tag 等于没写。详见 `engine/README.md`。
> 2. **方案必须落成目录**：`schemes/<id>/` 至少包含 `README.md`（本标准的六段）·
>    `deploy.sh` · `run.sh` · `meta.json`。只写在聊天里的方案视为未交付。
> 3. **引擎必须有还原路径**：能 pull、能离线包 load、或能用仓库里的补丁 rebuild，三者至少一条，
>    并在卡片里写明是哪一条。三条都不成立的新方案，一律不许记为「可用」。

## 2. 口径（这些是唯一标准，不许自创）

| 指标 | 定义 | 单位 / 精度 |
|---|---|---|
| 单流 tok/s | `completion_tokens / (总时长 − TTFT)`，服务端 usage 计数 | 1 位小数 |
| 四档均值 | 四个 real 用例的算术平均（**不是** 7 档平均） | 1 位小数 |
| 区间 | 同一测试 N 轮的 min~max，**必须给** | 1 位小数 |
| ITL | `(总时长 − TTFT) / (completion_tokens − 1)` | ms，1 位 |
| acc/draft | 接受 token ÷ draft 数 | 3 位 |
| 稳态聚合 | 各流 tok/s 之和（不含 TTFT 排队） | 1 位 |
| 墙钟聚合 | `总 token ÷ (最后一个请求结束 − 第一个请求开始)` | 1 位 |
| prefill tok/s | 多点 (prompt_tokens, TTFT) 最小二乘**斜率**的倒数 | 整数 |
| 固定开销 | 同上回归的**截距** | s，2 位 |
| KV 峰值 | 测试期间 `vllm:kv_cache_usage_perc` 的**最大值** | %，1 位 |
| 启动时长 | 容器首行日志 → 首次 `/health` 200 | 分:秒 |

**五条铁律**

1. **单个数字必须带区间**。同一配置不同 nonce 之间就能差 5~7%，差值 <5% 一律写「噪声内」，禁止写「提升 / 优化了」。
2. **配对才可比**。跨方案比较必须用**同一批 nonce**；不同批 nonce 的绝对值不能直接相减。
3. **冷启动首轮丢弃**，不许用高熵用例单独下结论。
4. **四档必须全列**，最差的一档单独标出来。PP4 在 4 线程时 zh 只有 29.0，只看均值就会放过这个致命伤。
5. **代价和否定项必须写**。不写「GPU4 被占了」「TTFT 退 46%」「batch 8192 试过没用」的方案，下一轮一定重踩。

## 3. 样例：PP5 `fast`（当前生产基准，v1.1 全字段）

### 【PP5 fast】dspark k=5 + `cpu_threads:[28,4]` + engram SSD
> 单流 82.5 tok/s（四档均值），5 卡全占，prefill 4.7k tok/s → ✅ 生产基线

**A 元信息**

| 项 | 值 |
|---|---|
| 日期 / 编号 | 2026-11-14 · PP5-BASELINE |
| 引擎 | `18gogogo/170hx4-256r-dsv41-1017-flash:sm80`，未改源码 |
| 模型 | 1017 原版 ☑（未改权重、未量化） |
| 用例 | cases_v1 · sha `ee98f898` · 3 轮 · nonce 51/52/53 |
| 硬件 | GPU 0-4 全占 · 主机内存 ~190 GiB |
| 启动参数差异 | 基准：`[5,5,5,4,21]` / `[28,4]` / k=5 / kv 524288（11-15 起） / batch 4096 |
| 脚本 | `run-pp5-dspthr.sh` ｜ 回滚 `run-pp5-prod.sh.bak-thr28` |

**B decode 单流**

| 用例 | 均值 | 区间 | ITL ms | acc/draft |
|---|---:|---|---:|---:|
| code_python | 100.1 | — | 46.3 | 0.753 |
| json_struct | 85.4 | — | 43.9 | 0.648 |
| zh_tech | 65.2 | — | 40.2 | 0.509 |
| math_steps | 79.1 | — | 40.5 | 0.498 |
| 四档均值 | 82.5 | — | 42.7 | — |
| C1_高熵 | 未测（v1.1 新增） | | | |

**C 首字与 prefill**

| 项 | 值 |
|---|---|
| 短请求 TTFT | 0.43 ~ 1.32 s |
| 22k 冷 TTFT | 9.40 s（归档文本） |
| 22k 重复文本 TTFT | 5.00 s |
| **prefill 斜率** | **4,683 tok/s** |
| 固定开销 | 2.10 s |

**D 并发**

D1 稳态扩展性（输入 ~300 tok，输出 300 tok）

| 并发 | 每路 tok/s | 稳态聚合 | ITL ms | TTFT max | preempt | KV 峰值 |
|---|---:|---:|---:|---:|---:|---:|
| 1 | 97.3 | 97.3 | 46.3 | 1.32 | 0 | — |
| 4 | 33.9 | 135.6 | 29.6 | 1.42 | 0 | 3.8% |

> 4 路时每步变快（ITL 46→30 ms），但每路分到的 token 只剩 1/3。
> 稳态聚合 136 vs 单流 97，**+40%**；墙钟聚合 117（差的那 19 是 TTFT 排队）。

D2 真实 4 路（每路输入 2.5k tok、输出 300 tok）

| 聚合 tok/s | 墙钟 | TTFT max | ITL 均值 | preempt | KV 峰值 |
|---:|---:|---:|---:|---:|---:|
| 62.4 | 19.2 s | 9.63 s | 40.9 ms | 0 | 25.4% |

> **2.5k 上下文下 4 路，TTFT 从 1.4 涨到 9.6 s**。原因是 `max_num_batched_tokens=4096`，
> 4 × 2.5k 的 prefill 被切成 4096 的块串行执行，后三路是在排队，不是算得慢。

**E 容量与上下文**

| 项 | 值 |
|---|---|
| max_model_len | **131,072**（128k） |
| KV 池 | **131,072 聚合 token = 22.37 GiB**（物理等效 133,969） |
| max_num_seqs / batched_tokens | 4 / 4,096 |
| 4 路均分每路可用上下文 | **32,768** |
| 不 preempt 的会话 × 上下文 | 4k→4 · 8k→4 · 16k→4 · **32k→4** · 64k→2 · 128k→1 |
| 实测越界点 | **4 × 37k（150k token）**，KV 99% 触顶 |
| 越界后的后果 | TTFT 9.5 → 36.4 s，墙钟聚合 62.4 → **1.7** tok/s（解码被饿死） |

> **容量不是 128k × 4，而是总共 128k。** 单会话塞满 128k 就把池子占完了，
> 4 个会话每个只有 32k 可用。这是 PP5 最容易被误解的一条。

**F 资源与代价**

- 显存：GPU0 47.8 / GPU1 51.8 / GPU2 52.3 / GPU3 51.5 / GPU4 58.6 GiB
- 专家：覆盖率 7216/7680 = 93.96% · GPU 命中 99.5~99.7% · CPU 路由 0.27%
- CPU：PP4 decode 4 线程（~410%）· prefill 28 线程（峰值 18.95 核）
- **服务启动时长：8 分 57 秒**（权重+5 卡上下文 3:56 ｜ engine init 4:54 ｜ 起服务 7 s）

**G 判定与边界**

- 验收线：单流 ≥40 tok/s → ✅ 通过，作为新一代基准
- 适用：单流长文生成、批量后台任务；不适用：4 路以上高并发（被 max_num_seqs=4 卡死）
- 已证伪：batch 8192（覆盖率降到 88.54%、全项掉）、decode 线程 8（步时不变、CPU 白烧）、Humming/Marlin 路线（sm80 无 FP8，模型绕过 FusedMoE）
- 回滚：`run-pp5-dspthr.sh` 已是生产，k=3 备份在 `.bak-k3`

## 5. 怎么测（探针用法）

```bash
cd bench   # 仓库根目录下

# 单流四档（冻结用例集，带 sha256 校验）
python3 run_cases.py <label> <nonce号> --set real

# 4 路稳态（短上下文）
python3 probe_capacity.py conc --label <label> --conc 4 --ctx 200 --out 300

# 4 路真实（长上下文，含 prefill 排队）
python3 probe_capacity.py conc --label <label> --conc 4 --ctx 2000 --out 300

# 容量边界（会打满 KV 池，跑之前确认没人在用）
python3 probe_capacity.py conc --label <label> --conc 4 --ctx 30000 --out 16

# prefill 斜率（三点回归，自动扣固定开销）
python3 probe_capacity.py prefill --label <label> --sizes 20,80,240

# 容量速算表（不打请求）
python3 probe_capacity.py table --kv-tokens 524288 --seqs 4
```

- 结果写 `bench/capacity.jsonl`（并发/容量/prefill）和 `bench/results.jsonl`（单流四档），两个文件分开，避免污染冻结用例集。
- 启动时长：`docker logs -t <容器> | head -1` 到 `docker logs -t <容器> | grep "GET /health" | head -1`。
